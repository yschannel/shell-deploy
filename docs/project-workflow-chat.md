# Shell 部署工具：第一版工作流程与协作方案

本文根据项目讨论整理，供两位开发者和辅助开发的 AI 参考。本文是设计记录，不是逐字聊天记录，也不代表下述功能已经实现。网络连接和 GitHub 登录排查不属于项目设计，未收录。

## 1. 项目定位

基于 Bash 编写一个部署与运行管理工具，在 Ubuntu 上自动完成指定应用的依赖检查、配置生成、编译部署和运行管理。

用户拿到包含应用代码和部署脚本的项目包后，通过少量命令和必要的配置选择，即可在自己的环境中启动应用。

第一版服务于一个指定的示例应用和一个明确的 Ubuntu 版本。脚本需要事先知道应用的依赖、编译方式、启动参数和就绪检查方法，不承担任意项目的自动识别与部署。

讨论以“可通过浏览器访问的 C++ 图书管理服务”为例。图书管理功能属于示例应用；Shell 项目负责部署和管理该应用。实际示例应用尚需两位开发者确认。

## 2. 第一版范围

计划提供以下命令：

| 命令 | 用途 |
| --- | --- |
| `bash deploy.sh setup` | 检查依赖、收集配置、创建目录、编译应用 |
| `bash deploy.sh start` | 启动应用并检查是否就绪 |
| `bash deploy.sh stop` | 停止本工具管理的应用进程 |
| `bash deploy.sh restart` | 停止后重新启动应用 |
| `bash deploy.sh status` | 查看运行状态 |
| `bash deploy.sh logs` | 查看应用日志 |

配置支持默认值和自定义值，首版至少包括服务端口和数据目录。

暂不纳入第一版：版本更新与失败回滚、跨 Linux 发行版支持、图形界面、复杂菜单及任意项目自动部署。

## 3. 用户完整体验

### 3.1 获取项目

用户下载解压或克隆项目，进入项目根目录：

```bash
cd shell-deploy
bash deploy.sh setup
```

### 3.2 检查并准备依赖

脚本检查系统是否符合支持范围，并检查示例应用需要的依赖，例如 `g++`、`make` 和用于响应检查的 `curl`。实际依赖清单以选定应用为准。

示例输出：

```text
正在检查运行环境……
[通过] 当前系统符合要求
[通过] 已安装 g++
[通过] 已安装 make
[缺少] curl
是否安装缺少的依赖？[y/N]：
```

用户同意后才安装系统依赖，需要管理员权限时由系统提示输入密码。用户拒绝安装时，说明缺少的依赖和手动安装方法，并以失败状态结束初始化。安装失败时同样停止，不能继续报告初始化成功。

### 3.3 选择配置

```text
请选择配置方式：
1. 使用默认配置（推荐）
2. 自定义配置
请输入 [1]：
```

建议默认端口为 `8080`，默认数据目录为项目根目录下的 `data`。自定义时逐项询问，直接回车采用默认值：

```text
请输入服务端口 [8080]：
请输入数据目录 [./data]：
```

端口输入不合法或已被占用时，说明原因并要求重新输入。自定义数据路径须正确处理空格，并检查目录能否创建或使用。

### 3.4 自动完成初始化

脚本创建所需目录、生成本地配置并编译应用：

```text
[完成] 创建数据和日志目录
[完成] 生成配置文件
[完成] 编译应用
初始化成功！
执行以下命令启动服务：
bash deploy.sh start
```

任一步骤失败，显示失败原因及可用的日志位置，返回非零状态。重复执行 `setup` 时，不应直接覆盖用户已有配置，具体交互需开发前确定。

### 3.5 启动与使用

```bash
bash deploy.sh start
```

脚本检查程序及配置是否存在、是否已运行、端口是否可用，然后启动应用并在限定时间内检查就绪状态。

```text
正在启动服务……
正在检查服务响应……
[成功] 服务已就绪
访问地址：http://localhost:8080
日志位置：项目目录下的 logs/app.log
```

上述地址适用于浏览器与服务在同一台机器上的情况。在 Ubuntu 虚拟机里运行服务时，Windows 浏览器的 `localhost` 不指向虚拟机；从宿主机访问的方式需要另行配置并验证。

用户随后使用应用自身的业务功能。Shell 工具继续负责状态、日志、停止和重启。

### 3.6 日常管理

- 重复执行 `start`：提示服务已运行，不启动第二个实例。
- 执行 `status`：显示真实状态，不能仅凭 PID 文件存在就判断运行中。
- 执行 `logs`：显示日志；日志不存在时给出明确提示。
- 执行 `stop`：只停止本工具管理的应用，已停止时给出提示。
- 执行 `restart`：先停止再启动，并检查结果。
- 应用启动失败或立即退出：返回失败，提供排查信息。

## 4. 目录结构

```text
shell-deploy/
├── README.md                   # 用户使用说明
├── deploy.sh                   # 命令入口
├── scripts/
│   ├── common.sh               # 少量共用函数
│   ├── setup.sh                # 环境初始化模块
│   └── service.sh              # 运行管理模块
├── src/                        # 示例应用源代码
├── Makefile                    # 编译规则
├── config.example              # 配置模板
├── docs/
│   └── project-workflow-chat.md # 本设计记录
└── .gitignore
```

运行时生成，通常不提交 Git：

```text
config.conf     # 用户本地配置
bin/app         # 编译后的应用
data/           # 应用数据
logs/app.log    # 应用日志
run/app.pid     # 记录应用进程 ID
```

建议 `.gitignore` 内容：

```gitignore
/bin/
/data/
/logs/
/run/
/config.conf
```

Git 不记录空目录。`src` 初始为空时可用 `.gitkeep` 占位；运行目录由 `setup` 创建。

## 5. 两人并行分工

| 开发者 | 负责文件与模块 | 主要任务 |
| --- | --- | --- |
| A | `scripts/setup.sh`，环境初始化 | 系统及依赖检查、安装确认、配置交互、目录创建、编译 |
| B | `scripts/service.sh`，运行管理 | 启动、停止、重启、状态、日志、PID 与响应检查 |
| 两人共同 | `deploy.sh`、`common.sh`、配置约定、示例应用、说明文档 | 确定接口、连接模块、完整验收 |

主入口只负责识别命令和调用模块。共用模块保持简单，修改公共接口时及时通知另一人。B 可先使用双方约定的示例配置和已编译程序开发，无需等待 A 的初始化模块完成。

## 6. 开发前必须确定的接口

以下是讨论中提出的建议，需双方确认后保持一致：

| 项目 | 建议约定 |
| --- | --- |
| Shell | Bash，使用 `bash deploy.sh ...` 调用 |
| 配置字段 | 至少包含 `PORT`、`DATA_DIR` |
| 配置模板和本地配置 | `config.example` 与 `config.conf` |
| 默认端口 | `8080` |
| 默认数据目录 | 项目根目录下的 `data` |
| 应用产物 | `bin/app` |
| 日志位置 | `logs/app.log` |
| PID 文件 | `run/app.pid` |
| 初始化函数 | `setup_project` |
| 服务函数 | `start_service`、`stop_service`、`restart_service`、`status_service`、`show_logs` |
| 返回值 | 成功 `0`，失败非零 |
| 路径处理 | 以脚本确定的项目根目录解析项目路径，正确引用包含空格的路径 |

还需确定：

1. 支持的 Ubuntu 具体版本和完整依赖清单。
2. 示例应用及其启动参数。`bin/app --port ... --data-dir ...` 仅为示例，必须与真实应用一致。
3. 配置文件的准确语法、生成和读取方式，尤其是带空格的路径如何保存。
4. 应用以前台还是自行后台化方式运行。建议由脚本管理前台应用的后台进程。
5. 就绪检查接口，例如 `/health`；该接口必须由应用实现。
6. 启动等待时限、停止等待时限、日志展示方式。
7. 已有配置、过期 PID 文件、启动失败时的处理方式。

停止进程前需确认进程属于本应用，避免 PID 被其他进程复用造成误操作。不要通过宽泛的进程名匹配停止不相关程序。

## 7. 分阶段开发

### 第一轮：最短流程

A 实现默认配置、目录创建和编译；B 实现启动、状态查询和停止。尽早合并并验证：

```bash
bash deploy.sh setup
bash deploy.sh start
bash deploy.sh status
bash deploy.sh stop
```

### 第二轮：正常交互

A 补齐依赖检查、安装确认和自定义配置；B 补齐日志、重启和启动响应检查。

### 第三轮：失败处理与交叉验收

两人测试异常情况，完善 README。A 测试 B 的运行管理；B 在干净的 Ubuntu 测试环境里按 README 测试初始化流程。

## 8. Git 协作

- `main` 保存经过共同验证的版本。
- A 使用 `feat/setup` 分支，B 使用 `feat/service` 分支。
- 每完成一个独立功能就提交，提交信息说明具体变化。
- 推送后通过 Pull Request 请求另一人检查，再合并到 `main`。
- 尽早合并可运行的进展，不等全部功能完成才首次集成。
- 不提交令牌、密码、本地配置、日志和编译产物。

目录骨架由一人创建并合并到 `main` 后，另一人拉取，双方再基于共同版本开始开发。

## 9. 如何借助 AI

两位开发者向各自的 AI 提供同一份已确认的接口约定。每次只请求一个明确的小功能，要求说明命令作用、失败处理和验证方式。

A 的提问示例：

> 我负责 Ubuntu 部署工具的 setup 模块。请按本项目接口约定实现依赖检查函数，列出缺少的依赖，安装前征求用户确认，拒绝或安装失败时返回非零。请解释关键命令，并给出验证方法。

B 的提问示例：

> 我负责运行管理模块。请按接口约定实现 start_service，检查程序和配置，避免重复启动，记录 PID，并在限定时间内检查应用是否就绪。失败时返回非零并提供日志位置。请解释后台进程和 PID 的处理方式。

采用 AI 代码前，开发者应能说明它执行了什么、失败时如何处理，以及实际验证过哪些场景。涉及管理员权限、删除文件和停止进程的代码需逐行理解。

## 10. 第一版验收清单

- [ ] 指定 Ubuntu 测试环境按 README 能完成初始化与启动。
- [ ] 默认配置和自定义配置均可使用。
- [ ] 缺少依赖时能正确提示，同意或拒绝安装的流程正确。
- [ ] 编译失败时停止初始化并报告原因。
- [ ] 未初始化时启动，能给出操作提示。
- [ ] 无效端口或端口占用时有明确提示。
- [ ] 重复初始化不会直接覆盖用户配置。
- [ ] 重复启动不会产生多个实例。
- [ ] 应用无法就绪或立即退出时不会误报成功。
- [ ] 状态、日志、停止和重启结果符合实际。
- [ ] 停止操作不会终止不相关进程。
- [ ] 从其他工作目录调用脚本仍能正常运行。
- [ ] 项目路径包含空格时正常运行。
- [ ] 仓库中没有敏感信息和运行产物。

最终目标：另一位开发者只看 README，在约定的 Ubuntu 环境中通过少量命令即可部署和使用示例应用。
